Submitting a scan report

This guide explains how a probe talks to the API, in prose. The precise types live in the OpenAPI contract, and the interactive reference lets you inspect and call the endpoint directly.

The shape of the exchange

A probe runs its entire assessment locally and submits the result once, after every test has finished. There is no session to open, no partial upload and no progress reporting. One scan run produces one request.

The API identifies two separate things: which probe is talking, from the token in the Authorization header, and which run the data belongs to, from the report_id the probe generates. One probe submits many runs over its lifetime; each run needs its own identifier.

Authentication

Every probe carries its own token, issued in the administration panel when the device is registered. The token is a 64-character string and is displayed exactly once, at the moment it is created: the system keeps only its hash, so it cannot be read back later. If a token is lost, an administrator issues a new one, which immediately invalidates the old. 

Authorization: Bearer 3f8a1c...c9d2

A token that no administrator recognises is rejected with 401. A token that belongs to a probe an administrator has switched off is rejected with 403 - the credential is fine, the device is simply no longer allowed to report.

The request

Send POST /api/v1/reports with a JSON body carrying two keys:

KeyMeaning
report_id A UUID the probe generates before the first test starts. It must be unique across all probes, so generate a fresh one for every run. This is what makes retrying safe.
report The complete scan document, as a JSON object. The API does not read inside it, does not validate its structure and depends on none of its fields. 
POST /api/v1/reports HTTP/1.1
Host: pensec.top
Authorization: Bearer <device token>
Content-Type: application/json

{
  "report_id": "0f1d4e9c-6a2b-4f7e-9d31-5c8ba0f2e7a4",
  "report": {
    "scan_time": "2026-08-16 13:38:12",
    "orchestrator_ip": "192.168.0.107",
    "discovered_hosts_count": 9,
    "hosts": ["192.168.0.1", "192.168.0.100"],
    "nmap_results": { "192.168.0.1": "Starting Nmap 7.95 ..." }
  }
}

The report must be a JSON object, not an array. A top-level list is rejected with 422, because the contract promises an object and a list would quietly change the shape of everything stored downstream.

Size

A body larger than 32 MB is refused with 413. Retrying an oversized document will not help; it has to get smaller. Raw scanner output for a large network is the usual reason to approach that limit.

What comes back

A stored report answers 201. The body repeats what was saved, so the probe can confirm the whole document arrived: 

{
  "success": true,
  "message": "Report stored.",
  "data": {
    "report_id": "0f1d4e9c-6a2b-4f7e-9d31-5c8ba0f2e7a4",
    "status": "received",
    "received_at": "2026-08-16T13:41:02Z",
    "payload_bytes": 17581,
    "payload_sha256": "960d0ea4da06a7bb..."
  }
}

payload_bytes and payload_sha256 describe the document as stored. Note that the API stores a canonical re-encoding of the JSON you sent - semantically identical, but with your whitespace and escaping normalised - so the checksum will not match one computed over your exact bytes. Compare against the value returned here, not against your own file.

status is received, meaning the raw document is stored and nothing has been derived from it yet. Parsing is a separate, later step, and more status values will appear as it lands.

Retrying is safe

If the connection drops mid-upload and the probe cannot tell whether the report arrived, it should simply send the same request again. Submitting a report_id that is already stored answers 200 instead of 201, with the details of the report stored first. Nothing is duplicated and nothing is overwritten.

The first document wins. If a retry carries different content under the same report_id, the stored document is not replaced - the response describes what was already on file. Use a new report_id for a new run, never for a corrected version of an old one.

When something fails

Every failure answers in the same envelope, carrying a stable code. Branch on that code, never on message, whose wording can change at any time. 

{
  "success": false,
  "code": "device_token_invalid",
  "message": "Unknown device token."
}
StatusCodeWhat the probe should do
401 device_token_missing
device_token_invalid		 Do not retry. The token is absent or unknown; it has to be fixed on the device.
403 device_disabled Do not retry. An administrator switched this probe off.
413 payload_too_large Do not retry unchanged. The document exceeds 32 MB.
422 validation_failed Do not retry unchanged. The errors object names the offending fields.
429 rate_limit_exceeded Wait for the period in the Retry-After header, then retry.
500 server_error Retry later. The report was not saved; the failure is on our side.

Submissions are limited to 30 per minute per probe. A device that reports once per scan will never come close; the limit exists to contain a malfunctioning or hostile client.

A complete example

With curl, sending a document straight from disk:

curl -X POST https://pensec.top/api/v1/reports \
  -H "Authorization: Bearer $PENSEC_TOKEN" \
  -H "Content-Type: application/json" \
  --data-binary @submission.json

From the probe itself, in Python:

import json, uuid, time, requests

REPORT_ID = str(uuid.uuid4())      # generated before the scan starts

def submit(report: dict, token: str) -> None:
    body = {"report_id": REPORT_ID, "report": report}

    for attempt in range(5):
        response = requests.post(
            "https://pensec.top/api/v1/reports",
            json=body,
            headers={"Authorization": f"Bearer {token}"},
            timeout=120,
        )

        if response.status_code in (200, 201):
            return                                   # stored, or already stored

        payload = response.json()

        if response.status_code == 429:
            time.sleep(int(response.headers.get("Retry-After", 60)))
            continue

        if response.status_code >= 500:
            time.sleep(30 * (attempt + 1))
            continue

        raise RuntimeError(f"refused: {payload['code']}")   # 401, 403, 413, 422

Note that the same REPORT_ID is reused across every attempt. That is what makes the retry loop safe: whichever attempt gets through, the run is stored exactly once.

What the API does not do

  • It does not parse the report or require any field inside it.
  • It does not accept partial results while a scan is running.
  • It does not push anything back to the probe, and never initiates a connection.
  • It does not modify a stored document, ever.

The document is kept exactly as received precisely so that improving the analysis later can never cost data already collected.
